# The lean MR and its line map

*Measured 2026-09-10 by the Opus compiler partner. The final compiler builds from
`compact` — comment bytes and the lines they empty are both gone — and every
location it reports for a rendered file names the SOURCE instead. `<evidence>` is
the station-local build directory; this repository is public, so machine-specific
absolute paths are not recorded here. The sha256 is the identity that matters.*

## The decision, and what it cost

`keep` remains a declared member of `-Dmachine-lines`; nothing was removed and
nothing is defaulted. The final executable now builds from `compact`.

| | bytes | vs source |
|---|---|---|
| source | 61,693,025 | — |
| MR (`compact`) | 57,107,031 | **−7.43%** |
| line maps | 4,713,466 | 8.25% of MR |
| **MR + maps on disk** | **61,820,497** | **+0.21%** |

**Stated plainly because it matters to the goal:** what the compiler READS is
7.43% leaner. The tree as a whole, maps included, is 0.21% *larger* than the
commented source. The leanness is in the compile input, not in the footprint.

## The map

- **A product of rendering.** Each entry is recorded inside the loop that decides
  which lines to drop, never reconstructed afterwards by diffing the output —
  a reconstruction could disagree with what was actually written.
- **A sidecar**, `<file>.zig.linemap`, next to the rendered file. Chosen over one
  table in the manifest for a reason that decides it: at error time the reporter
  already holds the rendered file's absolute path, so a sidecar is one `open` +
  one `read` to answer one question, while a manifest table would mean parsing an
  index over all 1,146 rendered files to resolve a single diagnostic. Diagnostics
  must not pay tree-scale cost. The sidecar also travels with the file it
  describes, so a half-copied tree cannot pair a map with the wrong source.
- **Declared once.** `src/LineMap.zig` holds the format, the writer and the
  reader. `tools/machine_tree.zig` imports it as a named module. There is no
  second spelling to drift.
- **Self-verifying.** The header carries a digest over the recorded path and the
  table. Without it a single flipped entry that stays in range is undetectable
  and answers wrongly forever — see P3.

### The column needs no mapping, and that is proven

A Zig line comment runs to end of line, so **no code can follow a comment on the
same line**. Rendering therefore only ever removes a line SUFFIX, and `compact`
removes whole lines, never parts of them. The code prefix of any surviving line
is byte-exact, so the column is already correct and is passed through untouched.
This is a structural consequence of the tokenizer's grammar *and* it is checked
per line by the renderer's column law, not assumed.

## P1 — the map law and the column law

Over the whole tree, per line, not per file:


**1,155,610 rendered lines checked, 0 mismatches.** For each, the tokens of the
rendered line equal the tokens of the source line the map names, and the rendered
line is a byte prefix of it.

## P2 — the diagnostic law

Error planted at **source line 12**, behind three comment lines, two doc-comment
lines and a trailing comment on the failing line itself; it renders to line 4, so
the two numbers cannot coincide. Verbatim, on the full LLVM compiler:

```
.../lm_src/prog/main.zig:12:21: error: type 'u8' cannot represent integer value '300'
    const bad: u8 = @as(u32, 300); // a trailing comment on the failing line
                    ^~~~~~~~~~~~~
referenced by:
    middle: .../lm_src/prog/main.zig:19:9
    main:   .../lm_src/prog/main.zig:23:11
```

Source path, source line **12**, column **21**, the **full** source line text
including the trailing comment the rendered line does not have, the caret under
`@as(u32, 300)` — and every location in the `note:` chain resolved (source lines
19 and 23, the true lines of those two calls). No rendered path or line appears
anywhere in the program's own diagnostics.

## P3 — a corrupted map is refused, never answered

One entry tampered from source 12 to source **11** — in range, plausible, and
exactly the kind of corruption a reader cannot reason its way out of:

```
thread N panic: line map '.../main.zig.linemap' is present but unusable (Corrupt).
Refusing to report a source location from it: a wrong line in the wrong file is
worse than none. Re-render the machine tree, or remove the map to report
rendered locations.
```

Restored → md5 `b9197f1cb9a8572c607bde95e92e8192` identical → green again at line
12. Format-level refusals are unit tested (4/4): truncation, bad magic,
unsupported version, a tampered table entry and a tampered path.

**Named limit:** the refusal is FATAL. That is the right trade for this failure
class — a wrong line in a real file is worse than a stopped compile — but a
corrupt map aborts the compile rather than degrading to rendered locations.

## Item 4 — the price of resolving DEBUG-INFO line tables (NOT implemented)

Priced as asked; the decision is the owner's.

**It is not applied today, and here is the proof rather than the claim** — the
P3 panic trace above printed a frame as
`<evidence>/mtree_compact/src/Zcu/PerThread.zig:2019:21`: a rendered path and a
rendered line. Runtime panic traces and debuggers still point into the machine
tree.

**Where the line program is built** — three sites, all in the LLVM backend:

| Site | What it sets |
|---|---|
| `src/codegen/llvm/FuncGen.zig:2323` (`airDbgStmt`) | `prev_dbg_line = base_line + dbg_stmt.line + 1` — **once per statement** |
| `src/codegen/llvm/FuncGen.zig:524` | the subprogram (function) line |
| `src/codegen/llvm.zig` `getDebugFile` | the DIFile — **the file recorded in the line table** |

`base_line` and `dbg_stmt.line` compose additively, so the map must be applied to
the **sum** at 2323, never to the parts.

**Can the source path be the primary file with the MR path absent? Yes.** The
DIFile is built from a path string in `getDebugFile` and nothing downstream
re-derives it, so substituting the map's recorded source path there is
sufficient and complete for the file half.

**Cost per emitted line:** one bounds check and one `u32` load — *provided* the
map is cached per file on `Object`, beside the existing `debug_file_map`. That
cache is a **requirement, not an optimization**: without it this becomes a file
open per statement.

**Smallest hunk:** ~10 lines across three files — one `Object` field, ~4 lines in
`getDebugFile`, ~2 lines at each of the two `FuncGen` sites. `FuncGen` already
holds `object` and `nav_index`, so no new plumbing is needed.

**Interaction to watch:** `debugContentIdentity` hashes `file.sub_file_path`. It
does not read the DIFile, so changing the recorded path does not move the debug
identity — but anyone later folding the mapped path into that hash would change
it, and should say so.

## P5 — measurements, dated, medians of three (five for the lookup)

| Measurement | Median | Runs |
|---|---|---|
| renderer cold, `compact` + maps | **16.10 s** | 16.05 / 16.10 / 16.39 |
| renderer warm, `compact` + maps | **17.02 s** | 16.85 / 17.02 / 17.03 |
| renderer cold, `keep` (identity maps, no table) | 14.71 s | 14.73 / 14.56 / 14.71 |
| renderer cold, `src/` only (no 161 MB mirror) | 3.92 s | 3.85 / 3.92 / 4.05 |
| one diagnostic **with** the map | **0.48 s** | 0.48 / 0.46 / 0.49 / 0.48 / 0.48 |
| one diagnostic **without** the map | **0.47 s** | 0.49 / 0.47 / 0.47 / 0.46 / 0.47 |

**The map table costs 1.39 s** — the `keep` → `compact` difference at identical
file count and identical mirror, which isolates it — to build and write
1,155,610 entries.

**The error-time lookup is not distinguishable from noise here:** 0.48 s against
0.47 s, a ~10 ms difference on a 0.47 s compile, at or below the 0.46–0.49 spread.
That is one `open` + `read` + digest of a 197-byte file per diagnostic file, with
no cache. It is NOT a claim that resolution is free at scale — a compile
reporting errors across hundreds of distinct files would re-read a map per file,
and that case was not measured.

**Warm is slower than cold**, and the reason is structural rather than anomalous:
a cold run creates ~22,000 files and writes them, while a warm run READS all
~22,000 destination files to compare before writing none.

**A discrepancy I am not papering over:** packet 4 recorded a 2.15 s cold render
of the same 19,851-file mirror, against ~14.7 s for the equivalent `keep` render
today. The two absolute numbers are not comparable across occasions and I cannot
account for the gap from the data I have; only the within-session `keep` versus
`compact` difference (1.39 s) is a controlled comparison, and only that is used
above.

## Residuals

1. **Debug-info line tables still report rendered locations** — item 4, priced
   above, not implemented. Demonstrated by the P3 panic trace.
2. **Mirrored `.c` files report the rendered path** in C diagnostics
   (`Compilation.zig:1071` takes a plain file name, not a `Compilation.Path`).
   Line numbers are unaffected — C files are mirrored byte-identically — so only
   the path differs.
3. **A corrupt map is fatal**, not degrading (above).
4. **The tree with maps is 0.21% larger than the source** on disk.
5. **P2/P3 were first verified on a no-LLVM diagnostics compiler**
   (`68822bd3…`, 525 s, 1.3 GB peak) because the host's memory guard killed the
   full build twice. Both were then **re-verified on the full LLVM compiler
   `5f5ff986…`**, which is what the results above report. The no-LLVM binary is
   explicitly not a promotion candidate.
6. **`compact` is what the final binary uses; `keep` has no P4 build** on this
   packet's code.
